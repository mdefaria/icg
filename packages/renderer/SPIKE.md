# S5 — Renderer fidelity spike

## Goal

Prove that `@resvg/resvg-wasm` can produce believable Overlays for all four Platforms (TikTok, Instagram, YouTube, X) in both themes and both variants, and settle how colour emoji get onto the canvas. Fix the Template contract that C3 builds on.

## What was built

`packages/renderer` (`@icg/renderer`), no changes to `packages/shared` or `packages/host-sdk`.

- `renderOverlay(spec: OverlaySpec, assets): Promise<Overlay>` parses the spec with the shared zod schema, lays the comment card on a transparent full-Frame canvas at the Placement (x, y normalised, anchored at the card centre, `scale` multiplies the natural size) and rasterises it. Natural size: the card is laid out in phone points and drawn at 3 px/pt, so scale 1 matches a 1080 px wide phone screenshot (`DENSITY = 3`).
- `renderCommentSvg(comment, template, scale, assets?)` returns the card alone as a standalone SVG; `renderCommentPng` rasterises it (used for the 2x crops and the golden tests).
- `initRenderer(source?)` initialises the wasm once. With no argument it reads `index_bg.wasm` from the package through `node:fs`; a browser passes a fetched `Response`/`WebAssembly.Module`.
- Templates in `src/templates/`: `tiktok.ts`, `instagram.ts`, `youtube.ts`, `x.ts`, each with a dark and light palette and a `single` / `creator-reply` layout. Shared pieces in `templates/card.ts`: wrapped paragraphs with inline emoji, avatars with the three `Avatar` kinds, verified badges, chips, the creator heart-with-avatar badge.
- Text layout in TypeScript (`wrap.ts`): greedy word wrapping, long-word splitting, emoji clusters as atomic tokens that may break between each other, explicit newlines, `maxLines` with ellipsis. Measurement (`fonts.ts`) is a per-glyph advance table read from the bundled TTFs with `opentype.js` (cmap + hmtx + kern/GPOS pairs). Each line becomes its own `<text>` run plus positioned `<image>` emoji; resvg only has to shape one line at a time, so measurement drift can at most change spacing within a line, never cause an overflow.
- Emoji (`emoji.ts`): `Intl.Segmenter` graphemes classified with `\p{Emoji_Presentation}` / `\p{Extended_Pictographic}` plus VS16, ZWJ, skin tone, keycap and regional-indicator rules; file name mapping for Noto (`emoji_u2764_200d_1f525.svg`) and Twemoji (`2764-fe0f-200d-1f525.svg`), fallbacks from full sequence to base emoji, an `EmojiLoader` interface and an in-memory implementation. Noto for TikTok/Instagram/YouTube, Twemoji for X.
- Avatars (`assets.ts`): `pool` loads PNG/WebP by id from a directory (six procedural placeholders in `fixtures/avatars/`, generated by `scripts/make-avatars.ts`), `user` takes the data URL as is, `default` draws a letter avatar or a grey silhouette.
- Like counts (`format.ts`): `formatCount(n, { platform, language })`.
- Fonts: Inter 400/500/600/700 and Roboto 400/500/700 as static TTFs (1.04 MB total) in `fonts/`.
- `scripts/samples.ts`: 16 full 1080x1920 frames, 16 card crops at 2x, one 3840x2160 frame, and timings. `scripts/profile.ts` breaks the render time down by card content. `scripts/instance-fonts.py` documents how the static fonts were produced. `src/golden.test.ts`: pixelmatch against committed goldens. Unit tests for wrapping, emoji segmentation, count formatting and the render boundary.

## How to run

```sh
pnpm install
pnpm --filter @icg/renderer samples        # writes packages/renderer/samples/*.png and prints timings
pnpm --filter @icg/renderer test           # unit + golden tests
pnpm --filter @icg/renderer golden:update  # re-baseline goldens after an intentional Template change
pnpm --filter @icg/renderer exec tsx scripts/profile.ts   # render-time breakdown
pnpm check                                 # whole repo
```

Review artefacts: `samples/<platform>-<theme>-<variant>.png` (full Frame), `samples/*.crop2x.png` (card at 2x), `samples/tiktok-dark-creator-reply.4k.png`.

## Findings

### Colour emoji: fonts do not work in resvg-wasm 2.6.2, inline SVG images do

Probe (`Hello world 😂👍🏽👨‍💻 ñandú` in Inter with an emoji font supplied through `fontBuffers`):

| Font                                             | Format            | Result          |
| ------------------------------------------------ | ----------------- | --------------- |
| NotoColorEmoji-Regular.ttf (Google Fonts, 25 MB) | CBDT/CBLC bitmaps | `.notdef` boxes |
| Noto-COLRv1.ttf (noto-emoji repo, 5 MB)          | COLRv1            | `.notdef` boxes |
| Twemoji.Mozilla.ttf 0.7.0 (1.5 MB)               | COLRv0            | `.notdef` boxes |

The wasm embeds `fontdb 0.14.1` and `rustybuzz 0.7.0`, i.e. a resvg from mid-2023, before COLR/bitmap glyph support landed. It also does not do per-character font fallback inside a `font-family` list: with `font-family="Inter, Noto Color Emoji"` the emoji render as Inter's `.notdef`, and with the emoji family alone every ASCII character becomes the emoji font's `.notdef`. A newer resvg would fix the format problem but not the fallback problem, and no Twemoji COLR font is maintained anyway.

Inline `<image href="data:image/svg+xml;base64,...">` renders Noto and Twemoji SVGs correctly, including gradients and ZWJ sequences, so that is the path. Emoji are segmented in TypeScript and placed as 1.2 em images on a 1.25 em advance. Missing emoji render as a blank advance and are reported in `buildCard().missingEmoji` so the UI can warn instead of showing tofu.

Nested SVG images are expensive, though: resvg re-parses and re-renders each embedded emoji SVG on every render (Noto's files carry gradients and dozens of paths). Profiling the TikTok creator-reply card at 1080x1920 (`scripts/profile.ts`):

| Card content                                            | Render         |
| ------------------------------------------------------- | -------------- |
| full card, 3 emoji as nested SVG, 2 pool avatars, text  | ~420 to 550 ms |
| same, emoji removed                                     | ~110 ms        |
| same, letter avatars instead of PNGs                    | ~85 ms         |
| same card with the 3 emoji pre-rasterised to 128 px PNG | ~86 ms         |

So the renderer now rasterises each distinct emoji SVG once with resvg itself, at a power-of-two size bucket (64 to 512 px, chosen from the emoji's pixel size at the requested scale) and embeds the cached PNG (`emoji-raster.ts`). Assets stay SVG, so any size works; the first render that meets a new emoji pays ~100 ms per emoji, every later render is fast. When `renderCommentSvg` is called before the wasm is initialised (a browser preview in an `<img>`), it falls back to the SVG data URLs.

Asset size, measured on the 17-emoji test set: Noto SVG 4.2 KB average (7.2 KB with the 54 KB 🎬 outlier), so roughly 4 to 7 MB per 1,000 uncompressed, about a third of that gzipped; Twemoji 1.5 KB average, roughly 1.5 MB per 1,000. The full set is ~3,700 files each (flags are PNG-only in Noto). Plan: ship Twemoji complete, ship Noto for the emoji the Bank actually uses plus a loader for the rest, or move the Noto set to a lazily fetched pack. Twemoji is CC-BY 4.0 (attribution required in the app's credits); Noto SVGs are Apache 2.0.

### Fonts

- resvg ignores variation axes: the Google Fonts variable `Inter[opsz,wght].ttf` renders every weight as Regular. `scripts/instance-fonts.py` (fonttools) instances static weights at `opsz=14` and subsets them to Latin, 190 KB each for Inter and 92 KB for Roboto. Total 1.04 MB, well under the 4 MB budget, leaving room for italics or Cyrillic later.
- Substitutes: TikTok uses TikTok Sans / SF Pro → Inter; Instagram uses SF Pro (iOS) / Roboto (Android) → Inter; YouTube uses Roboto → Roboto, exact; X uses Chirp → Inter. Inter is a close enough stand-in for SF Pro at phone sizes; Chirp is noticeably narrower with a more geometric "a", visible on the X card when compared side by side.
- `opentype.js` 2.0's shaper throws on Inter's `ccmp` chained-context lookups, so measurement does not go through `getAdvanceWidth`; it sums per-glyph advances plus kerning pairs. Inter's contextual alternates (`calt`) are applied by rustybuzz at render time and not by the measurer, so a line can be a pixel or two off its measured width. It has not caused a visible overflow in any sample.

### Fidelity gaps I know about

Compared against memory of the current apps (no reference screenshots could be fetched in this session; the layouts should be checked against real screenshots on a phone before C3 locks them):

- TikTok: real app shows display name in grey semibold above the text, time and "Reply" below, heart column on the right with the count under it, which is what the card does. The "Pinned" label position (after the name) and the "Creator" chip styling are approximations. The heart icon is Material's, slightly heavier than TikTok's. No "View N replies" row in the single variant.
- Instagram: username + time on the first line, text, then "Reply" is right. The heart is tiny on IG; count under the heart matches the Reels sheet. The real verified seal is a scalloped blue badge; the one here is a 12-point star with a check. "Author" chip for the creator reply is from memory and may be wrong. "See translation" was dropped because it only appears when the comment language differs from the UI language.
- YouTube: 24 pt avatar, `@handle • time` header, Roboto 14, thumbs up/down and reply bubble match the mobile app. YouTube's icons are thinner Material Symbols; these are the older filled Material outlines. The creator handle sits in a grey pill, which is right; the "liked by creator" heart badge appears after the thumbs-down, which is right.
- X: 40 pt avatar, bold name + badge + grey handle and time on one line, thread line between avatars, action row with reply/repost/like/views counts and bookmark/share on the right. The bookmark icon is dropped when the Spanish view count ("133,4 mil") does not fit at this card width. X has no "liked by creator" or "Creator" chip, so those Comment flags are ignored on X. Repost/view counts are derived from the like count because the Comment schema has no fields for them.
- All cards are flat rounded rectangles with no border or shadow. A light card on light footage will need a subtle shadow or border; resvg supports `feDropShadow`, not tried.
- The `creator-reply` variant assumes `comment.reply` is present; if it is missing the card falls back to `single`.

### Render times (Node 22, wasm, this container)

Median of repeated `renderOverlay` calls for the TikTok dark creator-reply sample (3 emoji, 2 pool avatars, 6 lines of text), including SVG build, rasterisation and PNG encoding, with the emoji raster cache warm:

| Frame            | Median         | PNG    |
| ---------------- | -------------- | ------ |
| 1080x1920 (9:16) | ~90 to 140 ms  | 91 KB  |
| 1920x1080 (16:9) | ~90 ms         | 76 KB  |
| 3840x2160 (4K)   | ~330 to 380 ms | 185 KB |

Fixed costs measured separately: wasm init 35 to 40 ms; an empty transparent 1080x1920 canvas costs ~85 ms (12 ms render, ~70 ms PNG encode) and an empty 4K canvas ~300 to 430 ms, so at 4K the PNG encoder is now the floor. Loading the seven font buffers into fontdb per render is not measurable. Before the emoji raster cache the same frames took ~370 to 420 ms at 1080p and ~1.6 s at 4K. The first render of a session adds roughly 100 ms per distinct emoji. ADR 0003's native-resvg escape hatch for Resolve is not needed on these numbers; the CEP and Electron hosts still have to be measured (S1/S4).

### Like-count formatting

Decided and encoded in `format.ts`, tests in `format.test.ts`:

- English: `< 1,000` plain; `1,000 to 9,999` is `1.2K` on YouTube, plain `1234` on TikTok, grouped `1,234` on Instagram and X; from 10,000 everywhere `12.4K`; millions `1.2M`. Values are floored (1,299 → `1.2K`), which is what the apps do.
- Spanish: the apps localise the suffix, so `12,4 mil` and `1,2 M` with a decimal comma and dot grouping (`1.234`). Confirmed from memory for Instagram, YouTube and X; TikTok's Spanish UI may keep `K`, to be verified on a device.

## Open questions

1. `OverlaySpec` carries no language, so UI copy ("Reply"/"Responder", "Pinned"/"Fijado") and number formatting come from `assets.locale`, defaulting to `en`. Either `Template` or `OverlaySpec` should carry a `language` (additive change to `packages/shared`, proposed for C1/C3).
2. `Comment` has no reply count, repost count or view count; X and YouTube show these. Derive them in the engine or add optional fields.
3. Full emoji set delivery: bundle Twemoji (5.5 MB raw) and lazily load Noto, or ship both in the installer and skip them on the web until first use.
4. The emoji raster cache lives in process memory; the Hosts could persist the PNGs next to the SVGs so the first-render cost disappears, or the asset pack could ship PNGs at 128 px and keep SVGs only for 4K.
5. CEP/Electron timing for 4K needs measuring on a real machine (S1/S4); Node numbers here are an upper bound for the same wasm.
6. Reference screenshots: every layout above is from memory. One afternoon with a phone and the four apps will settle the remaining pixel questions before C3.
