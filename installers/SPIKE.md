# S3 spike: installers for the Premiere CEP panel and the Resolve plugin

## Goal

Scripts and a CI release job that produce a signed, notarised macOS `.pkg` and a signed Windows `.exe` which install the Premiere CEP extension (`com.icg.premiere`) and the Resolve Workflow Integration plugin (`com.icg.resolve`) into the system folders, let the user pick Hosts (defaulting to the ones detected), ship uninstallers, and, above all, make the Premiere panel load **without `PlayerDebugMode`**.

### Verified here (Linux container)

- `bash -n` and `shellcheck 0.9.0` clean on every shell script (`sign-cep.sh`, `fetch-zxpsigncmd.sh`, `build-pkg.sh`, `uninstall.sh`, three `postinstall`).
- `distribution.xml` and the fixture `manifest.xml` are well-formed (`xmllint`).
- `release.yml` parses as YAML.

### Not verified here (no macOS, Windows, Premiere or Resolve in this environment)

- Any actual run of `ZXPSignCmd`, `pkgbuild`, `productbuild`, `productsign`, `notarytool`, `stapler`, `ISCC.exe`, `signtool.exe`. No `pwsh` in the container either, so `build.ps1` has not even been parsed.
- The central claim that a signed ZXP extracted into the extensions folder loads without `PlayerDebugMode` (see Findings 1 and 2 for why it is expected to, and the checklist's negative test).
- Distribution XML JavaScript (`system.files.fileExistsAtPath`, `system.compareVersions`) behaviour in the Installer app.
- Inno Setup `WizardSelectComponents`, `HKLM64`, `FindFirst` usage and the `/S` Sign Tool quoting with `$q`.
- Exact `ZXPSignCmd -verify` output strings (the scripts rely on exit codes only).
- Whether notarisation accepts Blackmagic's `WorkflowIntegration.node` after re-signing it with our Developer ID (expected; re-signing third-party Mach-O is standard Electron practice).
- Exact file names of the ZXPSignCmd binaries inside `ZXPSignCMD/4.1.3/{macOS,x64}` (the GitHub tree listing only showed folder names), hence the URL-by-variable approach.

## Findings with sources

1. **CEP validates signatures when loading from the extensions folder; `PlayerDebugMode` is only a bypass of that check.** Adobe's cookbook, section "Debugging Unsigned Extensions": "you can bypass the check for extension signatures by editing the CSXS preference properties file" (`HKEY_CURRENT_USER/Software/Adobe/CSXS.12` `PlayerDebugMode=1`, `defaults write com.adobe.CSXS.12 PlayerDebugMode 1`). There is no host-side "install" step: hosts only scan folders ("CEP first searches the product extension folder, then the system extension folder, and finally per-user extension folder"; "If two extensions have same extension bundle ID, the one with higher version is loaded"). So the thing that must be valid at load time is the folder, i.e. the ZXP's contents including `META-INF/signatures.xml` and `mimetype`. Source: [CEP 12 HTML Extension Cookbook](https://github.com/Adobe-CEP/CEP-Resources/blob/master/CEP_12.x/Documentation/CEP%2012%20HTML%20Extension%20Cookbook.md) (sections "Extension Folders", "Debugging Unsigned Extensions", "Signing Extensions"); same text in the [CEP 11.1 cookbook](https://github.com/Adobe-CEP/CEP-Resources/blob/master/CEP_11.x/Documentation/CEP%2011.1%20HTML%20Extension%20Cookbook.md). Adobe's packaging guide adds the outcome table: no signature or invalid signature: "the extension does not run"; expired certificate without timestamp: does not run; expired certificate with valid timestamp: "runs normally" ([Package, Distribute, Install](https://github.com/Adobe-CEP/Getting-Started-guides/blob/master/Package%20Distribute%20Install/readme.md)).

2. **Extracting the signed ZXP into the extensions folder is what the ecosystem's installers do.** Adobe's own `ExManCmd` and Anastasiy's manager put "extensions ... at the root level of the extension folder" (same guide). aescripts' FAQ gives the manual equivalent: rename `.zxp` to `.zip`, unzip, drop into `/Library/Application Support/Adobe/CEP/extensions` or `C:\Program Files (x86)\Common Files\Adobe\CEP\extensions`, and states their extensions "are signed and timestamped" ([aescripts ZXP/UXP Installer FAQ](https://aescripts.com/knowledgebase/index/view/faq/zxp-installer-faq/), read via search snippets; the site is not reachable from this session). bolt-cep's README: "Only an installed ZXP with `yarn zxp` will work without PlayerDebugMode enabled", and dev builds (symlinked, unsigned) require it ([hyperbrew/bolt-cep](https://github.com/hyperbrew/bolt-cep/blob/master/README.md)). `ZXPSignCmd -verify` itself accepts an `<extensionRootDir>`, i.e. Adobe expects signatures to be checked on folders. Counter-signal: a small 2025 tool, ZXP-Magic, extracts ZXPs but "Skips META-INF/ (ZXP signature files), not needed for local installs" while also shipping a PlayerDebugMode toggle ([Grimno/ZXP-Magic](https://github.com/Grimno/ZXP-Magic)); unclear whether that works without debug mode. Our installer keeps `META-INF` and `mimetype` (zero cost) and the checklist's negative test settles it empirically.

3. **ZXPSignCmd usage and the timestamp trap.** `ZXPSignCmd -selfSignedCert <countryCode> <stateOrProvince> <organization> <commonName> <password> <outputPath.p12> [-validityDays n]`; `ZXPSignCmd -sign <inputDir> <outputZxp> <p12> <p12Password> -tsa <url>`; `ZXPSignCmd -verify <zxp>|<extensionRootDir> [-certinfo] [-skipOnlineRevocationChecks]`. Adobe's examples use `http://time.certum.pl/` and `http://timestamp.comodoca.com/rfc3161`; after GeoTrust's TSA was shut down in 2017 the community moved to `http://timestamp.digicert.com/`, re-confirmed working in 2019 ([CEP-Resources#115](https://github.com/Adobe-CEP/CEP-Resources/issues/115)). vite-cep-plugin signs with the same `-sign` form and retries over a TSA list, falling back to unsigned-timestamp only when explicitly allowed ([hyperbrew/vite-cep-plugin zxp.ts](https://github.com/hyperbrew/vite-cep-plugin/blob/master/src/lib/zxp.ts)). `sign-cep.sh` never falls back. Symlinks and `__MACOSX`/`.DS_Store` inside the extension cause blank panels / invalid signatures ([CEP-Resources KnownIssue2024](https://github.com/Adobe-CEP/CEP-Resources/blob/master/ZXPSignCMD/KnownIssue2024.md)), hence the staging clean-up.

4. **Extension folders and CEP versions.** System: `/Library/Application Support/Adobe/CEP/extensions`, `C:\Program Files (x86)\Common Files\Adobe\CEP\extensions` (and since CEP 6.1 also `C:\Program Files\Common Files\Adobe\CEP\extensions`). Premiere Pro 15.4 ships CEP 11, Premiere Pro 25.0 ships CEP 12 (cookbook table), so Premiere 23/24 are CEP 11 and 25/26 CEP 12; the fixture manifest targets CEP 11 which loads in both. PlayerDebugMode keys are per CEP version (`CSXS.11`, `CSXS.12`), which the checklist checks.

5. **Resolve plugin location.** Blackmagic's Workflow Integration README (mirrored at [ResolveDevDoc](https://resolvedevdoc.readthedocs.io/en/latest/readme_workflow.html), not reachable from this session, confirmed through search snippets and three plugin repos): macOS `/Library/Application Support/Blackmagic Design/DaVinci Resolve/Workflow Integration Plugins/`, Windows `%PROGRAMDATA%\Blackmagic Design\DaVinci Resolve\Support\Workflow Integration Plugins\`; Resolve scans the root at startup, reads each plugin's `manifest.xml`, and lists it under Workspace > Workflow Integrations; Studio only; plugins are not supported on Linux ([auto-editor plugin](https://github.com/llucasandersen/auto-editor-davinci-plugin), [Timeline Utility](https://github.com/bryanrandell/DaVinci-Resolve-Timeline-Utility), Blackmagic forum threads). The README says the authoritative copy is the one installed with Resolve (`.../DaVinci Resolve/Developer/Workflow Integrations/README.txt`); S4 should confirm from it.

6. **macOS pipeline.** `notarytool submit --wait` with keychain profile / `--key --key-id --issuer` / `--apple-id --team-id --password`; flat installer packages are accepted and can be stapled; `notarytool log` should be read even on success; `altool` is dead since 1 Nov 2023 ([Apple, Customizing the notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)). Notarisation requires every Mach-O in the payload to be Developer ID signed with hardened runtime, so `build-pkg.sh` re-signs the Resolve payload, and `sign-cep.sh` offers `--codesign-identity` to sign any Mach-O inside the CEP folder before the ZXP signature is computed (signing afterwards would break the ZXP hash).

7. **Inno Setup specifics.** `SignTool` signs Setup, the uninstaller and Setup's temporary self-copies (otherwise Defender ASR can block them); the Sign Tool must be defined in the IDE or via ISCC `--signtool=<name>=<command>` (`/S`), with `$f` the quoted file, `$q` a quote; `SignToolRetryCount` default 2 ([issrc ISHelp/isetup.xml](https://github.com/jrsoftware/issrc/blob/main/ISHelp/isetup.xml), fetched raw since jrsoftware.org is blocked here). `[Components]` with `Types: full` plus an `iscustom` type gives the per-Host picker. GitHub's `windows-2025` image ships Inno Setup 6.7.1 and Windows SDK 10.0.26100 (signtool) ([runner-images Windows2025-Readme](https://github.com/actions/runner-images/blob/main/images/windows/Windows2025-Readme.md)).

8. **Windows signing market, 2026.** OV/EV keys must be on FIPS 140-2 L2 hardware since 1 June 2023, so a PFX in CI is out. Azure Trusted Signing, renamed Artifact Signing in 2026, costs USD 9.99/month (Basic, 5,000 signatures) or USD 99.99/month (Premium); organisations in US/CA/EU/UK (plus more countries per 2026 third-party lists), individuals US/CA only; Microsoft's MSIX docs state a three-year verifiable tax history for organisations while a Microsoft moderator said there is no minimum age, reports conflict ([Microsoft Code signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options), [Q&A thread](https://learn.microsoft.com/en-us/answers/questions/5977141/azure-artifact-signing-trusted-signing-is-a-us-llc), [azure/artifact-signing-action@v2](https://github.com/Azure/trusted-signing-action), timestamp `http://timestamp.acs.microsoft.com`). Traditional OV: SSL.com USD 129/year list + eSigner cloud signing USD 15/month; Sectigo via resellers USD 219 to 225/year; DigiCert USD 400 to 549/year, tokens USD 120 to 249 ([SSL.com](https://www.ssl.com/products/software-integrity/signing-service/), [SSL Dragon](https://www.ssldragon.com/blog/code-signing-certificate-providers/), [SSL2BUY](https://www.ssl2buy.com/digicert-ov-code-signing-certificate.php)). Microsoft's own pages were not reachable from this session; prices come from search snippets of those pages and resellers and must be re-checked at purchase time.

9. **Host detection without Host APIs.** macOS: Premiere installs as `/Applications/Adobe Premiere Pro 20xx/Adobe Premiere Pro 20xx.app`, Resolve as `/Applications/DaVinci Resolve/DaVinci Resolve.app` (free and Studio share the path; Studio-only is a messaging problem, not a detection one). Windows: community sources point at `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\App Paths\Adobe Premiere Pro.exe` and per-version keys under `HKLM\SOFTWARE\Adobe\Premiere Pro\` (older docs), and `HKLM\SOFTWARE\Blackmagic Design` for Resolve (Blackmagic forum). None is authoritative for 2026 builds, so `icg.iss` ORs registry checks with folder/exe existence under `Program Files`.

## Open questions

1. **Does CEP 11/12 really reject a folder without `META-INF/signatures.xml` when PlayerDebugMode is off?** Everything points to yes, but one tool claims the opposite. The checklist's negative test answers it in five minutes on the owner's machine. If CEP does not check, the whole signing step is still harmless and still required for the Marketplace-free "ZXP" artefact, but the README wording changes.
2. **Signature check and timestamps offline.** aescripts notes their installer "may fail to verify the signature if it cannot properly access the Internet". Does the Host itself attempt online revocation checks at load time, and what happens on an offline edit suite? Test with Wi-Fi off after install.
3. **Does notarisation accept Blackmagic's `WorkflowIntegration.node` re-signed with our Developer ID**, and does Resolve still load it afterwards (it may verify its own signature)? If Resolve rejects a re-signed `.node`, the alternative is to leave it untouched and see whether notarytool accepts Blackmagic's Developer ID signature as is.
4. **ZXPSignCmd binary distribution.** Exact file names and whether the macOS binary is notarised (the fetch script strips quarantine). Alternatives: commit the binaries under `installers/tools/` (licence check needed) or vendor them in a private release asset.
5. **Trusted Signing eligibility for the owner's UK company** (age requirement). Decides between USD 10/month and roughly USD 300/year + cloud signing.
6. **Resolve Studio vs Free on the installer side.** Both share the application path, so the installer cannot warn Free users precisely; the landing page copy carries that (PLAN section 2). Checking `Info.plist` bundle identifiers in Distribution JavaScript is possible once the Studio bundle id is confirmed.
7. **Per-user fallback.** The installers require admin and use system folders only. Should a per-user install (`~/Library/Application Support/Adobe/CEP/extensions`, `%APPDATA%\Adobe\CEP\extensions`) exist for locked-down agency machines? CEP supports it; Resolve's README only documents the system folder.
8. **Upgrade behaviour.** `InstallDelete`/wholesale replacement is right for CEP, but ICG settings/Activation data must live outside the plugin folders (C5 licensing) or they are wiped on upgrade.
